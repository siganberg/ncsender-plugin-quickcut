# Contributed changes: angled patterns, Measure Pattern Angle, Keyhole, unit entry, Drill, holding tabs

This file describes a set of changes contributed to QuickCut, written so the maintainer can review them, revise them, or have Claude Code re-apply them to a different version of the code. It records what changed, why, the decisions behind it, and how it was verified.

Base: `v0.1.14` (commit `1c891ef`). The version number in `manifest.json` was deliberately left alone, so `.scripts/release.sh` can bump it.

## Summary

| Feature | What it does |
| --- | --- |
| Angled Linear / Honeycomb patterns | New **Angle (°)** input on every Linear/Honeycomb pattern. Spacing becomes center-to-center **along** the angled row, and row spacing is measured **across** it. An optional **Rotate shapes** switch is available on Rectangle, Polygon, and Keyhole. |
| Pattern extent | An **Extent** switch on Linear/Honeycomb patterns: the distance fields become first-to-last center and the copies are spread evenly over it (CAD's "Extent" linear pattern). Flipping it converts the values so the pattern doesn't move. |
| Circular Total Angle | A **Total Angle** field (default 360°) on Circular patterns. 360 is the old even spacing; less spreads the copies from Start Angle to Start + Total with copies on both ends; negative is clockwise. |
| Help page | A **Help** button pinned above Close opens help for the current tab: hand-written notes plus every field tooltip on that tab, collected from the page, so touch users can read them. Back returns. |
| Rectangle Start Angle | A **Start Angle** field (beside Cut Type) turns the rectangle about its center, CCW; the preview now draws the corner radius (in proportion to the shorter side) and the angle. |
| Polygon Corner Radius | A **Corner Radius** field (beside Cut Type) rounds every corner of the polygon, for profile, clearing and tabs; the preview draws it. |
| Pattern layout | The Pattern card is two rows (Style / Angle / switches, then X Count / X Spacing / Y Count / Y Spacing), 330px → 192px tall. |
| Measure Pattern Angle | A page (no sidebar button) that shows the angle and distance from the work origin to a second point, typed in or copied from the live machine position with **Grab Current**. **Use …° for** *shape* puts the angle in that shape's pattern. |
| Measure link | A **Measure** link beside each pattern Angle label is the only way into the measure page. Use or Back returns you to that shape. |
| Keyhole tab | New shape for keyhole / T-slot bits: single plunge, slot out, retrace to the hole, retract at the hole. Supports all patterns and a Slot Angle. Has a to-scale preview. |
| Unit entry | Length and feed fields accept `.25in`, `.25"`, `1/4"`, `1-1/2"`, `6.35mm`, `0.635cm`, and, for feeds, `100ipm` / `in/min` / `mm/min` / `mm/m` plus per-second `mm/s` / `in/s` / `ips`. Values are converted on blur to a plain number in the active units. |
| Drill tab | New tab for point holes the size of the bit: single plunge or pecking (full retract to clear chips, or short back-off to break them), optional dwell. Supports Linear, Honeycomb, and Circular patterns, and Circle's origin picker. |
| Holding tabs | Rectangle, Circle, and Polygon Inner (perimeter) / Outer cuts can leave bridges on the final passes. Tabs sit mid-edge on straight sides; the previews show where. |
| Pattern preview | With Pattern on, a to-scale preview beside the pattern fields draws every copy's toolpath, plunge points and X0 Y0, from the tab's own generator, and updates as you type. |
| Docs | The README gains Keyhole, Drill, Holding tabs, Patterns, Measuring an angle, and Typing units sections. It also fixes the stale "Polygon — coming soon" line. |

## Invariants these changes respect

- **Generator twins stay identical.** Generator code exists twice: inline in `config.html` and in `lib/quickcut-gcode.cjs` (the copy the tests load). Every generator change was made in both. The same rule now covers `parseUnitValue` (`config.html` and `lib/unit-input.cjs`); `tests/unit-input.test.cjs` fails if those two copies differ.
- **0° is byte-identical to before.** `applyGridAngle` returns the positions untouched when the angle is 0. A test asserts that a pattern with `angle: 0, rotateShapes: true` produces exactly the same G-code as a pattern with no angle at all.
- **Saved settings stay compatible.** New pattern fields (`angle`, `rotateShapes`) default to 0 / false when absent. The new `keyhole` and `drill` settings blocks are independent of the others, and a shape's `tabs` block is optional.
- **Tabs off is byte-identical to before.** With tabs off (or on a clearing cut, or with Tab Height ≥ Total Depth), the depth passes and laps are the original code path. This was checked against the committed generator on 576 cases.
- **Page-wide listeners belong to one dialog open.** The tool-menu dialog runs the script inline in the host page, and every open runs it again. Listeners on `document` or `window`, and timers, would outlive the dialog and act on the next open's elements (same ids) using the earlier open's state.
  - **Rule:** each such listener checks `rootAlive()` and removes itself once its own `.qc-wrapper` (`ROOT`) is detached. The unit-entry blur listener also ignores fields outside `ROOT`.
  - **Bug this prevented:** opening in metric, then reopening in imperial, converted `200ipm` to 5080.
- **Toolpath conventions are unchanged.** Keyhole reuses `programHeader`, `startupBlock`, `programFooter`, `safeHopDelta`, the 2 mm slow-plunge start, and `xyDp` decimals, so it matches the existing shapes.

## Feature details

### 1. Angled Linear / Honeycomb patterns

**Generator** (`lib/quickcut-gcode.cjs` and the inline twin in `config.html`):
- **`applyGridAngle(positions, pattern)`**:
  - After the Linear/Honeycomb grid is built in its local frame, every position is rotated about the first instance by `pattern.angle` (degrees, CCW from +X), using the existing `rotatePoint`.
  - When `pattern.rotateShapes` is true, each position's `rotDeg` is set to the angle. The Rectangle and Polygon emitters already turn instances by `rotDeg`, as do the Circular "Path Direction" patterns, so no emitter changes were needed. Circles ignore `rotDeg`.
- **`rotatedBbox(bbox, deg)` + `computePatternAnchorShift`**:
  - The origin anchor now uses each instance's rotated extents instead of the unrotated shape bbox.
  - **Behavior change / bug fix:** this also corrects the existing **Circular (Path Direction)** style when the origin is a corner or an edge midpoint. Details are below.

**Circular (Path Direction) origin fix — before and after.**

With a pattern on, the Origin setting anchors the outer boundary of the whole pattern. The original code built that boundary from each copy's position plus the *unrotated* shape size. Circular (Path Direction) turns each copy, so for non-round shapes the boundary was wrong, and cuts could run past the chosen origin.

Example: a 20 × 10 rectangle, outer cut, bit 0 (so the toolpath is the part outline), Circular (Path Direction), 4 copies, radius 40. The top and bottom copies are turned 90° and are 20 tall, but the old code counted them as 10 tall.

| Origin | Original code (X range, Y range) | Fixed |
| --- | --- | --- |
| front-left | X 0 to 100, **Y −5** to 95 | X 0 to 100, Y 0 to 100 |
| back-right | X −100 to 0, Y −95 to **+5** | X −100 to 0, Y −100 to 0 |
| front-center | X −50 to 50, **Y −5** to 95 | X −50 to 50, Y 0 to 100 |
| center | X −50 to 50, Y −50 to 50 | unchanged |

- **Effect of the old bug:** with front-left, the old code cut 5 mm past Y0, off the front edge of stock zeroed on its corner.
- **What triggered it:** Circular (Path Direction), a rectangle or polygon, and any origin except center. The overhang is half the difference between width and height.
- **Impact on existing users:** anyone who had shifted their origin to compensate will see those parts move by that amount.
- **Regression test:** `circular-follow with a corner origin keeps every cut inside the origin corner` in `tests/quickcut-gcode.test.cjs` pins this. It fails against the `v0.1.14` code and passes now.
- **Unaffected:** center origins and Linear/Honeycomb patterns without rotation. All pre-existing tests still pass.
- **`patternDescription`** appends ` angle=36°` (and ` rotated`) to the header comment when the angle is non-zero.

**UI** (`config.html`):
- **Layout (two rows):** the top row (`.qc-row-3.qc-pattern-top-row`) holds Pattern Style, the Angle field (`.qc-pattern-grid-only`, hidden for Circular) and a switch cell (`.qc-pattern-toggle-cell`) with Symmetric Ends (Honeycomb) and Rotate shapes (`.qc-pattern-angled-only`, angle ≠ 0 on a grid style). The cell is hidden when neither switch shows. The second row is `.qc-row-4.qc-pattern-axis-row`: X Count, X Spacing, Y Count, Y Spacing; Circular is one `qc-row-3` (Count, Radius, Start Angle). Below 760px the axis row goes 2 × 2 and the switches move to their own line. This cut the Pattern card from 330px to 192px at normal widths. All five pattern cards share the same markup apart from the style options, defaults, and whether there's a Rotate switch (Circle and Drill have none).
- **`updatePatternAngleLabels(prefix)`:** swaps the four field labels (`data-pattern-label`) between:
  - *X Count / X Spacing / Y Count / Y Spacing* at 0°;
  - *Count / Spacing / Rows / Row Spacing* at any other angle, kept short so the four columns don't wrap, with the longer explanation (`PATTERN_TITLES`, e.g. "Center-to-center along the 30° row") in each label's tooltip.
- **Form plumbing:** `readPatternForm`, `packPattern`, `hydratePattern`, and the validation rules (metric + imperial) all carry `angle` and `rotateShapes`.

Decisions made with the requester:
- The rotate option is a per-pattern switch, not always-on or always-off.
- Labels switch dynamically, rather than always reading X/Y.

### 1a. Pattern extent

- **Generator:** `computePatternPositions` divides `xDist` / `yDist` by `count − 1` (`patternStep`, 0 for a count of 1) when `pattern.spacing === 'extent'`, before the grid is built, so angles, Honeycomb, anchor shifts and hole keys all follow unchanged. With `spacing` missing or `'spacing'` the output is byte-identical to before. `patternDescription` gives `extent X=…, Y=…; dX=…, dY=…` (spacings to 4 decimals).
- **Honeycomb:** the extent covers the primary rows (`xCount − 1` and `yCount − 1` steps); shifted rows sit half a step in, as before.
- **UI:** an **Extent** switch (`qc-<p>-pattern-extent`) first in each `.qc-pattern-toggle-cell`, shown for grid styles. `wirePatternExtent` converts both distance fields on change (× or ÷ `count − 1`; a count of 1 is left alone) so the pattern doesn't move, then fires `input`. `updatePatternAngleLabels` uses `PATTERN_LABELS.axisExtent` / `angledExtent` (*X Extent / Y Extent*, or *Extent / Row Extent* when angled) and sets the label tooltip to the spacing it works out to; a delegated `input` listener on the pattern body keeps that current.
- **Plumbing:** `readPatternForm` / `packPattern` / `hydratePattern` carry `spacing: 'extent' | 'spacing'`.
- **Tests:** positions match spacing mode with the worked-out step (Linear, angled, Honeycomb, count 1), and the header text.

### 1b. Circular Total Angle

- **Path Direction relative to the first copy:** `rotDeg` is now `angle − startAngle` (it was the absolute angle). The first copy, at the Start Angle, matches the shape preview, and each later copy is turned by how far round the circle it is. With Start Angle 0 nothing changes; with any other Start Angle, Path Direction copies come out turned by −Start Angle compared with before (requested after a Polygon at Start Angle 90 had its top copy turned 90° from the preview).

- **Generator:** `circularStep(totalAngle, count)` replaces `360 / count` in `computePatternPositions` (both twins; the inline one calls its variable `stepDeg`). Missing or `|total| ≥ 360` gives `±360 / count`, so 360 is byte-identical to before and −360 is a clockwise full circle. Otherwise `total / (count − 1)`, putting copies on both ends of the arc (0 for a count of 1). Path Direction uses each copy's own angle, so it follows. `patternDescription` adds ` total=N°` only when it isn't 360.
- **UI:** `qc-<p>-pattern-total-angle` (number, default 360) is the fourth field of the Circular row, now a `.qc-row-4.qc-pattern-axis-row`, so it wraps 2 × 2 with the grid row below 760px. Validation −360…360 in both rule blocks, plus `validateField` rejects 0. `readPatternForm` / `packPattern` / `hydratePattern` carry `totalAngle`.
- **Tests:** full circle matches the old positions, 90° and −90° arcs, −360°, Path Direction rotations, and the header.

### 1c. Rectangle Start Angle and preview

- **Generator:** `withShapeTurn(positions, params.startAngleDeg)` adds the angle to every copy's `rotDeg` in `generateRectangleProgram` and `generateRectangleClearingProgram` (both twins). The emitters, tabs and `computePatternAnchorShift` (via `rotatedBbox`) already handle per-copy rotation, so the origin anchors the turned part's box. 0 is byte-identical; otherwise the header's Corner Radius line adds `, Start Angle: N°`.
- **UI:** `#qc-rect-start-angle` sits between Cut Type and Origin (`.qc-row-3.qc-rect-type-row`: 1.4fr / 1fr / auto), so the card isn't taller. Validation −360…360 in both rule blocks; saved as `rectangle.startAngleDeg`.
- **Preview:** drawn to the shape's proportions (it was a fixed 76 × 46, so a square looked 5:3), fitted into at most 76 × 60, or an 80 diagonal when turned, with a 14 minimum side; `roundedRectPath` draws the corner radius in proportion to the shorter side (capped at fully round ends), and the outline, hatch, dimension arrows and tab marks turn by the Start Angle (CCW on screen); the labels stay upright.
- **Tests:** 0 unchanged for outer / inner / clearing, 90° swaps the extents, the header text, and the front-left origin on a turned rectangle.
- **Drag to turn:** `wirePreviewAngleDrag('qc-rect-preview', 'qc-rect-start-angle', true)`, and the same for Polygon. Relative mode turns the shape by however far the pointer turns about the preview center (a knob; a tap does nothing), since these shapes have no direction to point; Keyhole's Slot Angle stays absolute. Same whole-degree steps, 90° snap within 8°, and 0–359 result.

### 1d. Polygon Corner Radius

- **Geometry** (`computePolygonGeom`, both twins): a corner arc tangent to both edges has its center on a smaller *core* polygon with apothem `a − rc` (`rc` clamped to `a`, which is fully round). The tool path is that core grown by `arcR = toolApothem − coreApothem` (`rc + bit radius` outer, `rc − bit radius` inner). When `arcR ≤ 0` (an inner cut whose corner is no bigger than the bit) the sharp path stays, since the bit rounds the corner itself. `rc = 0` is byte-identical to before.
- **Path:** `roundedPolygonSegments` (CCW, starting where vertex 0's arc begins: arc about each core vertex spanning 360/n°, then the straight edge) feeds `polygonSegments` (so tabs follow), `emitOnePolygon` (`emitSegmentLap` writes line ends and arcs at 5 decimals, per the arc-tolerance note), and `emitOnePolygonClearingRounded` (rings larger than the core are rounded, inner ones sharp). Checked: worst arc start/end radius mismatch 0.0006 mm over 5168 arcs, inside grblHAL's 0.002 mm.
- **Origin box:** `polygonShapeBbox` uses the core polygon's box grown by `rc`.
- **UI:** `#qc-poly-corner` (unit field) between Cut Type and Origin, reusing `.qc-rect-type-row`. Validation 0…max plus `validateField` rejecting more than half the across-flats size. The preview draws the rounded outline (core polygon + arcs, sweep-flag 0) and spaces its tab marks along the same arcs and edges with the real tool-path lengths.
- **Tests:** 0 unchanged for all cut types, outer arc radius rc + bit radius, front-left origin, inner sharp fallback and inner arcs, clearing rings, tabs on the rounded path.

### 1f. Origin on a tapped corner (Rectangle and Polygon)

- **Values:** `corner:N` (1-based, in cut order: Rectangle front-left, front-right, back-right, back-left before turning; Polygon its vertices) or `shape-center` (Polygon's own center; Rectangle's center node just sets `center`). Any other value is a point of the pattern's box as before, so existing output is unchanged.
- **Generator** (both twins): `resolveShapeOrigin(params, positions, bbox, corners)` with `rectangleCorners(params)` / `polygonCorners(params)` (exported) returns the shift and the header label (`corner 3`, `shape center`). The corner is the first copy's, where the two edges meet even when rounded (what probing two edges finds), turned with the copy. A corner the shape no longer has falls back to `center (picked corner not on shape)`.
- **Preview:** the points aren't drawn (the origin crosshair, below, marks the Origin); `pickPreviewNode` takes the nearest within 8 units. `wirePreviewAngleDrag(..., true, onTap)` only starts a twist after the pointer moves 4 units, so a tap goes to `onTap` and a drag still turns the shape. The Origin inputs' `change` (9-dot clicks) redraws the preview so the highlight follows.
- **Tests:** corner 1 / 3 match the front-left / back-right dots unturned; corner 1 at 90°; a triangle's shape center vs box center; corner 2 of a triangle; the fallback.

### 1h. Origin inset

- **Generator** (both twins): `computePatternAnchorShift(origin, positions, bbox, inset)` moves the anchor outward by `inset` on each side the origin is on (`left`: −X, `right`: +X, `front`: −Y, `back`: +Y), so the cut moves inward. `insetApplies` limits it to corner and edge origins; `insetNote` adds `, inset N<units>` to the header's Origin line. Callers pass `params.inset`: Rectangle and Polygon through `resolveShapeOrigin`'s box branch, Circle's two programs, Keyhole's box origins, Drill through `resolveDrillOrigin(..., inset)`, and `shapeOriginOffset` for the crosshair. Picked corners, `shape-center`, picked holes and Keyhole's `hole` ignore it. Inset 0 is byte-identical. **Negative insets** (added with Slot) move the cut outward past the origin: `insetApplies` is `inset != 0`, validation allows −max..max, and the fields lost their `min="0"`. Its use case is rounding a stock corner with a Slot centre line (Radius = R + bit radius, Sweep 90, inset = −bit diameter), documented in Help and the README; tests cover all four corners.
- **UI:** `#qc-<p>-inset` (unit field) sits beside each Origin picker as its own column (`.qc-origin-inset-field`: `.qc-origin-col` + `.qc-inset-field`, labels level), so no card is taller. `updateInsetState` greys it out when the origin isn't a corner or edge; each preview calls it first, so dots, taps and hydration all keep it right. Saved per shape as `inset` (mm); validation 0…max.
- **Preview:** `insetPad` makes room: Rectangle fits W + 2·inset by H + 2·inset, Circle and Polygon shrink their drawing radius, Keyhole and Drill add 2·inset to their extent, so the crosshair at the stock corner stays in view.
- **Tests:** inset 0 unchanged; front-left, back-right, front-center and left-center on Rectangle; center and a picked corner ignore it; the juice-groove case; Circle, Polygon, Drill (and a picked hole), Keyhole box vs plunge hole.

### 1g. Origin crosshair on the shape previews

- Rectangle, Circle, Polygon and Keyhole previews draw Drill's crosshair (`originCross`, class `qc-origin-mark`) at X0 Y0, so the 9-dot picker and the preview visibly agree. The point comes from the generator's exported `shapeOriginOffset(shape, params)` (both twins): X0 Y0 relative to the first copy's center (Keyhole: its plunge hole), worked out exactly as the program does, including turned rectangles, picked corners, polygon shape center, and pattern boxes. Each preview maps it into its own drawing (Rectangle undoes the turn, scales each local axis as drawn, and turns back; the others scale uniformly). With a pattern the origin can fall outside the drawn copy; the crosshair is then left out (pinning it to the edge was confusing).
- `wireOriginCrosshairs` redraws these previews when the Origin input, the pattern switch, or any pattern field changes.

### 1e. Inner corners and the bit (Rectangle and Polygon)

- The Corner Radius field is never limited: it means the corner you want, so it stays valid when Cut Type or the bit changes. On an inner or clearing cut the bit can't cut tighter than its own radius, so:
  - `bitCornerNote(params, unitsLabel)` (both twins) appends ` (the bit leaves N)` to the header's Corner Radius when the bit's radius is larger (on Polygon the Corner Radius part then shows even at 0). The path is unchanged.
  - `previewCornerRadius(typed, cutType)` makes both previews draw the larger of the two, and `switchTab` now redraws the Rectangle and Polygon previews, since each tab loads its own bit.
  - Both Corner Radius tooltips say so.

### 2. Measure Pattern Angle page (`data-view="measure"`)

**Where the position comes from** (found by reading the ncSender source):
- `GET /api/server-state` returns `machineState.{MPos, WPos, WCO, workspace, status, connected}`, with positions as comma-separated `"x,y,z"` strings.
- When the dialog is opened from the tool menu, ncSender also posts `{type: 'server-state-update', state}` messages, and later messages are partial deltas. The Plugins-tab iframe never receives these messages.
- The tab therefore does both:
  - it listens for the messages, merging only the fields that are present;
  - it polls `/api/server-state` every 500 ms, but only while the tab is open.

**Second point (requested after first use):**
- The angle comes only from the **Second Point Coordinate** X / Y fields (one compact row with Grab Current; `qc-meas-px/py`, `data-unit="length"`, active units). They change only when typed in or when **Grab Current** (`captureCurrentPosition`) is pressed, so jogging after measuring can't change the angle by accident. The button label matches ncSender's own "Grab Current" wording.
- **Remembered:** the point is saved with the plugin settings as `measure: {x, y}` in mm (`saveSecondPoint`, on field change, after Grab Current, and on Use; only when it changed), and restored in `hydrateSavedSettings`. So the next dialog open, or a Measure link from another shape, starts with the same point. Clearing both fields clears it; a half-filled or unreadable point isn't saved.
- **Grab Current** fetches `/api/server-state` first, then copies the live work position, rounded like other displayed values. In imperial that rounding (0.0001") can move the angle by about 0.001°.
- The live table (work, machine, WCO) keeps updating as a reference. The old **Refresh** footer button was removed, since Grab Current reads a fresh position itself.

**Calculation:**
- The live work position is `MPos − WCO`, falling back to `WPos` (`liveWorkPos`). This keeps the work and machine readouts consistent when partial deltas update only some fields.
- Angle = `atan2(y, x)` of the second point, shown to 3 decimals in −180…180. Distance = `hypot(x, y)`, in the active units.
- When the point is within 0.01 mm of the origin, or a field isn't a number, the angle is "—" and the Use button is disabled.

**Behavior and lifecycle:**
- **Common cards:** the Tool, Spindle, and Save cards are hidden on this tab, because it generates no G-code.
- **Teardown:** the tool-menu dialog runs this script inline in the host page, so the timer and listener would outlive the dialog. `measureTabAlive()` stops polling once the tab's DOM is gone.

**Units:**
- ncSender passes positions through from the controller and treats them as mm (`$13=0`).
- With `$13=1` the angle is still right, but the distance and coordinates are not.
- The README documents this.

### 3. Measure link

- **Link:** `<a data-measure-for="rect|circ|poly|key|drl">` sits inside each pattern Angle label.
- **No sidebar button (changed after first use).** The page was first a sidebar tab with five Apply buttons. Since every use starts from a pattern, it's now reached only through the link, and centre/corner finding is left to ncSender's own probing screen.
- **`switchTab(view)`:** the sidebar click handler, pulled out so the link can open a view that has no button. While on the measure page the sidebar keeps the shape it came from highlighted, and the measure page is never saved as the last tab (`LAST_TAB_KEY`), so a reopened dialog lands on a shape.
- **`openMeasureFor(prefix)`:** opens the page, sets `measure.returnTo`, and names the shape in the title.
- **Footer:** **Back** (`closeMeasure`) returns without changes. **Use …° for** *shape* (`useMeasuredAngle`) sets the pattern angle, turns the pattern on, switches Circular to Linear, and returns. Its label shows the angle and shape, and it's disabled until there's a valid point.

### 4. Keyhole tab (`data-tab="keyhole"`, ids `qc-key-*`)

**Generator:** `generateKeyholeProgram` / `emitOneKeyhole`. For each instance:
```
G0 X<hole> Y<hole>
G0 Z<safe hop>
G0 Z<2 mm>
G1 Z-<depth> F<plunge>      ; single plunge, full depth
G1 X<end> Y<end> F<feed>    ; end = hole + slotLength at (slotAngle + rotDeg)
G1 X<hole> Y<hole>          ; retrace
G0 Z<safe hop>              ; retract only at the hole
```

Decisions made with the requester:
- **Origin defaults to the plunge hole.** With `origin: 'hole'` (or none), X0 Y0 is the first instance's hole and there's no anchor shift; pattern positions already start at (0, 0).
- **Origin picker (added later).** Like Circle's, plus a ring-shaped `hole` point, the default. The 9 grid points anchor the bounding box of every keyhole's footprint (the head, Bit Diameter, swept from hole to slot end), via `keyholeBbox` and `computePatternAnchorShift`, which now also accepts a function of the position for the bbox, because a keyhole isn't symmetric about its hole. Other shapes still pass a plain bbox and are unchanged. The picker grid stays square like the others and draws the footprint inside it at true proportions, centred (`updateKeyholeOriginPicker`); the ring sits on the drawn hole.
- **Single plunge, no Depth of Cut.** A shallower pass along the slot would widen the narrow neck slot to the full head width, so the slot is always cut at full depth.
- **Slot Angle default is 90°,** so the slot runs toward +Y from the hole.
- **Pattern rotation turns the slots.** Circular Path Direction, or Linear with Rotate shapes, adds `rotDeg` to the slot direction.
- **Bit Diameter is the head diameter.** The toolpath follows the bit's center, so the bit size is used only for the header comment and the preview.

**UI:**
- **Structure:** mirrors Polygon. Keyhole is added to `TOOL_SHAPES` (so it gets per-shape tool values), and has its own save/hydrate block (`body.keyhole`), validation rules, a pattern card cloned from Polygon's, and a Measure link on its pattern.
- **Preview** (`updateKeyholePreview`):
  - **Scale:** drawn to scale. The hole diameter is the Bit Diameter and the hole-to-end length is the Slot Length, fitted to the box. The hole is capped at about 44 units across so a 0-length slot still leaves room for labels.
  - **Rotation:** the drawing is turned to the Slot Angle. Labels are anchored away from the shape and clamped inside the box.
  - **Drag to set the angle:** `wirePreviewAngleDrag(svgId, inputId, relative)` (absolute here) uses pointer events (with pointer capture) on `#qc-key-preview`. The slot is drawn centered on the preview, so the angle is the pointer's direction from the center: whole degrees, snapping to a multiple of 90° within `PREVIEW_ANGLE_SNAP` (8°), normalized to 0–359. It writes `#qc-key-start-angle` and fires `input`, so the preview, origin picker and validation follow. `touch-action: none` on the preview stops a drag from scrolling the dialog.
  - **Redraws:** on Bit Diameter input, and on switching to the tab. Switching tabs swaps the Tool card values without firing an `input` event, which is why the tab switch triggers a redraw too.

### 5. Unit entry

**Parser:** `parseUnitValue(text, isImperial, kind)` (twin in `lib/unit-input.cjs`).
- **Accepts:** decimals, fractions, mixed numbers (`1-1/2`, `1 1/2`), and an optional sign.
- **Units:** `mm`, `cm`, `in`, `inch`, `inches`, `"` (curly `”` and `″` too). Feed fields also accept `mm/min`, `mm/m`, `in/min`, `in/m`, `inch/min`, and `ipm` (per minute), and `mm/s`, `mm/sec`, `in/s`, `in/sec`, and `ips` (per second, multiplied by 60).
- **Output:** a value with no unit is returned as-is, already in the active units. Converted values are rounded like `roundDisplay` (4 dp for inches, 3 dp for mm). Anything unreadable returns `null`.

**Wiring:**
- **Fields:** length and feed inputs are now `type="text"` with `data-unit="length|feed"`. A `type="number"` input discards `1/4"` before JavaScript can see it.
  - Counts, angles, RPM, delay, and stepover stay `type="number"`.
  - No `inputmode` is set, so on-screen keyboards keep letters and `"`.
- **Blur conversion:** a capture-phase `blur` listener on `document` normalizes the field. Capture runs before each field's own blur validation, so validation sees the converted number. It then dispatches `input` so previews refresh.
- **Safety nets:**
  - `num()` and `validateField` parse through `parseUnitValue`, so text that hasn't been converted yet is read correctly.
  - The depth cross-checks use `num()`.
  - `validateAll()` normalizes every unit field before validating, so Generate works even if a field never blurred.
- **Hint:** each unit field gets a `title` tooltip listing the accepted forms.
- **Arrow keys:** `wireArrowKeySteps` (one `keydown` listener on `ROOT`, so it goes when the dialog does) steps unit fields and `type="number"` fields on Up/Down with DevTools-style modifiers: 1, Shift 10, Alt/Option 0.1, and Ctrl/Command 0.001 (DevTools uses 100; the user wanted a fine step), in display units. It parses unit text first, uses the validation rules for `integer` (step at least 1) and `min` (a step below it clamps to it only if the minimum is a whole number, otherwise the value doesn't move, so it stays on the step grid), rounds to 3 (mm) or 4 (in) decimals, skips disabled fields, and fires `input`. Values over the maximum are left to validation.

### 6. Imperial starting values

The starting values in the markup are written in mm (Plunge Rate 1000, Feed 2000, Bit 3.175, and so on). On a fresh imperial install with nothing saved, they were read as inches, so Plunge Rate 1000 in/min failed the 500 in/min limit and Generate was blocked on every tab. This predates the other changes.

- **Fix:** `convertDefaultsToInches()` converts every `[data-unit]` field's starting value from mm to inches once, when the dialog opens in imperial, before `hydrateSavedSettings()` applies saved values on top.
- **Verified:** Generate works with untouched values on all 7 tabs in metric, in fresh imperial, and in imperial with saved settings (saved values still override).

### 7. Drill tab (`data-tab="drill"`, ids `qc-drl-*`)

- **Generator:** `generateDrillProgram` / `emitOneHole`. Per hole: `G0` XY, safe hop, 2 mm clearance, then pecks with `G1 Z F plunge`. Between pecks, `clear` mode rapids to the 2 mm clearance and back to 0.5 mm above the bottom; `break` mode backs off 0.5 mm. Optional `G4 P<dwell>` at full depth, then retract. The 2 mm and 0.5 mm are converted to inches in imperial.
- **No canned cycles:** G81/G83 aren't supported by plain grbl, and explicit moves show in the visualizer.
- **Origin:** Circle's 9-point picker (same markup and styling, default center), anchoring the box around all the holes via `computePatternAnchorShift` with a bit-sized circle bbox. A single hole at center is X0 Y0. The preview's crosshair marks X0 Y0, using the exported `computePatternAnchorShift`. `rotDeg` is ignored, and the pattern style list has no Path Direction option or Rotate switch, since a round hole has no direction.
- **Hole origin:** tapping the preview picks the nearest hole (within 1.5 × its drawn radius, at least 6 viewBox units) and sets the origin to `hole:<key>`. `patternPositionKeys` names each position in `computePatternPositions` order: `"col,row"` (1-based; Honeycomb's shifted rows are the even rows) or the copy number for Circular, so the pick survives count changes. `resolveDrillOrigin` (both twins, exported for the preview) returns the shift, the picked index for the highlight, and the header label (`Origin: hole at column 2, row 2`); a key the pattern doesn't have falls back to center with a note. No 9-dot point is active while a hole is picked.
- **UI:** one Hole card (Total Depth, Peck Depth, Peck Retract, Dwell, a to-scale plan preview of every hole with a crosshair on X0 Y0) plus the usual pattern card. Feed Rate is disabled on this tab (`relocateCommonCards`), because every move is at the Plunge Rate. The preview gets positions from the generator's exported `computePatternPositions`. Past `DRILL_PREVIEW_MAX` (2500, i.e. 50 × 50) holes it shows only the count and "too many to show" (no hole picking); it used to draw just the first 1500, which cut a row short and misplaced the crosshair.
- **Validation:** Peck Depth ≤ Total Depth; Dwell 0–10 s.

### 8. Holding tabs (Rectangle, Circle, Polygon)

- **Geometry:** each profile is turned into segments in work coordinates (`rectangleSegments`, `circleSegments`, `polygonSegments`), the same path the emitters cut, from the same start point. `tabIntervals` returns tab spans as distances along that path; each spans Tab Width + Bit Diameter, so Tab Width of material is left at the part.
- **Placement (`tabsOnEdges`):** tabs are shared among straight edges by length (largest remainder, ties to the edges the evenly spaced positions fall on), then centred along each edge. Collinear lines are merged, including the rectangle's bottom edge, which wraps through the mid-bottom start. Circles, and shapes whose edges are too short for their tabs, keep even spacing along the whole path.
- **A tab may cover the start point** (the rectangle's bottom tab does). `emitTabbedLap` makes its own entry plunge, going only to the tab top when the start is in a tab, and the lap then also ends lifted. A tab across the start is split into two intervals, one at each end of the lap.
- **Passes:** `depthLevels` adds a pass at exactly Total Depth − Tab Height. Passes at or above it are the original laps (and the circle's helix stops there); deeper passes are tabbed laps, which lift with `G1 Z<tab top> F<plunge> ; Tab` and drop back the same way. Lines and arcs are split at tab edges; arcs are re-emitted as G3 with I/J.
- **Header:** `(Tabs: 4 x 6mm wide, 2mm high)`, plus a warning when some or all tabs don't fit.
- **UI:** a Holding Tabs switch with Tabs / Tab Width / Tab Height in each Depth card, hidden for clearing. Previews draw dots where the tabs go, placed by the generator's exported `tabIntervals` on the preview outline with real (tool-path) edge lengths. Validation: Tab Height < Total Depth.

### 9. Section cards and spacing

- **`.qc-section-card`** (added beside `.qc-card` on all 20 cards in the scrolling panel) gives them the header cards' `--color-surface-muted` background, so the surface-coloured inputs stand out the same way. Previews, origin pickers, the keyhole hole ring, the unit badge, and the preview label halos / tab-mark outlines flip to `--color-surface` inside it. Frameless previews stay transparent (their rule comes later at the same specificity).
- **`--qc-section-gap` (12px)** on `.qc-wrapper` is the one step between sections: the header gap, header-card grid gap, panel gap, and the form's card-to-card gap (was 12 / 15 / 15 / 10). The header's bottom padding and the panel's top padding are half a gap each, so the header cards sit one gap above the first card, the same as card to card. The header has no bottom border: the filled section cards already separate it. Card padding matches the header cards (12px × 14px).

### 10. Help page (`data-view="help"`)

- **Entry:** `#qc-help-btn` (a `.qc-nav-btn` without `data-tab`, so `wireTabs` / `switchTab` skip it) in `.qc-sidebar-footer` above Close. `openHelp` renders for `state.currentTab` *before* switching (so per-tab tooltips such as Drill's disabled Feed Rate are still set), then `switchTab('help')`; `closeHelp` switches back. Help, like measure, is never saved as the last tab and hides the common cards; opened from the measure page, Back returns there with `measure.returnTo` kept.
- **Content:** `renderHelp(tab)` builds `.qc-section-card.qc-help-card` cards: the tab's `HELP_TOPICS` notes, then "<card> — field tips" from `collectHelpTips(section)`, then shared topics (Patterns on shape tabs, Tool / spindle / saving with the common cards' tips, Typing units incl. arrow keys), then a **More detail** card with one link to the QuickCut page of the ncSender manual (`HELP_DOCS`, https://docs.ncsender.xyz/plugins/quickcut/). It opens in a new window (`target="_blank" rel="noopener"`) and shows the full URL so it can be typed elsewhere.
- **`collectHelpTips`** reads every `[title]` in each card, names it from its `label[for]`, its own label text, its field's label, or "<card> switch", and skips the generic `Accepts …` unit hints, the pattern labels' angle-dependent tooltips, and the shared cards when they're relocated into the tab. So tooltips stay the single source; only `HELP_TOPICS` / `HELP_SHARED` need updating with the README when a feature changes.
- **Sidebar:** `.qc-sidebar` no longer scrolls as a whole; `.qc-sidebar-nav` scrolls instead, so Help and Close stay pinned on a short window.
- **Checks:** every tab opens its help, the view and sidebar highlight switch, no unit-hint noise, Back returns with values kept (and Drill's Feed Rate disabled again), help isn't remembered, and measure → help → back → measure → back.

### 11. Generate speed (File Manager save)

- **Finding:** the plugin's own work on Generate (validate + generate) is 2–9 ms here even for 300–400 KB patterns. The lag came from **Save to File Manager**: `saveGeneratedProgram` found a free name by probing `QuickCut/<name>`, `(2)`, `(3)`… with `GET /api/gcode-files/file`, which returns the whole file, one request after another, so it grew with every saved copy (40 copies = 41 sequential full downloads before the dialog closed).
- **Now:** `freeSavePath(filename)` reads one `GET /api/gcode-files` listing (tree of `{name, type, path, children}`; PascalCase handled too), picks the first free name, and confirms it with one probe (a quick 404), so an unexpected listing can never cause an overwrite; if the pick is taken it probes on from there as before. The lookup runs alongside `load-temp`; the save itself still waits for the load to succeed, before the dialog closes. `saveGeneratedProgram(gcode, path)` now just saves.
- **Feedback:** `loadGcodeIntoVisualizer` disables the tab's Generate button and shows "Generating…" until it resolves; it's restored on failure, or after 500 ms in case the dialog doesn't close.
- **Checks:** a browser test with a fake File Manager (40 saved copies): saved as (41) with one listing + one probe, listing sent with the load, save after it, PascalCase listing, an odd listing falling back to probing without overwriting, and no file requests with saving off.

### 12. Slot tab (`data-tab="slot"`, ids `qc-slt-*`)

- **Generator** (both twins): `generateSlotProgram` / `emitOneSlot`. `slotCenterline(params)` gives the centre line in local coordinates, normalised to run CCW: a straight slot is centred on (0, 0) (its overall Length less the width); an arc slot has its arc centre at (0, 0), so `shape-center` is the pivot. Chord / Rise / bulge Angle become R = (c²/4 + h²)/(2h), sweep = 4·atan(2h/c), centred on the bulge angle; a negative Sweep is flipped to run CCW from its other end. `placeSlot` turns it by a copy's `rotDeg` and moves it.
- **Paths:** `slotOutline(placed, d)` is the closed outline at half-width d, CCW: a stadium from the middle of one long side, or for an arc the outer arc, an end cap, the inner arc back **clockwise** (`dir: -1` segments, emitted as G2 by `emitSegmentPiece`; other shapes never set `dir`, so their output is unchanged), and the other cap. Cut types: `center` (the centre line, alternating direction each depth pass; width = bit), `inner` / `outer` (outline at half ∓/± bit radius, with holding tabs via `tabIntervals` / `emitTabbedLap`), `clearing` (the centre line out and back, then rings out to the inner outline, at most a stepover apart, each depth level).
- **Origin:** `slotOriginParts` gives `resolveShapeOrigin` a per-copy bbox (`segmentsBbox`, arcs exact) and the two end centres as `corner:1` / `corner:2`, so box origins, inset, taps and patterns behave as on Rectangle / Polygon. `shapeOriginOffset('slot', …)` feeds the crosshair.
- **Checks:** `slotProblem` (exported) catches missing sizes, width ≤ 0, an arc as wide as its radius, and ends that overlap (the gap between the end centres < width). The generator writes a warning and no cut; the Generate button shows the problem on the field to change instead. An inner or clearing cut no wider than the bit suggests Center line. Validation: Length ≥ slot width, Sweep ≠ 0, Depth of Cut ≤ Total Depth, Tab Height < Total Depth.
- **UI:** Slot Type (Straight / Arc) and Arc By (Radius & Sweep / Chord & Rise) choose which row of fields shows (`updateSlotFields`); Width is disabled for Center line; tabs are hidden for Center line and clearing (`updateTabsVisibility` / `tabMarks` now skip `center` too). The preview (`updateSlotPreview`) draws the generator's own outline to scale (an arc's centre kept in view unless that shrinks the slot by more than a quarter), the centre line dashed, a length or R dimension, tab dots on the tool path's real lengths, and the crosshair. `wirePreviewAngleDrag` now also accepts a function for its input, so a twist turns Angle, Start Angle or the bulge Angle, and an optional snap offset, so on an arc slot the 90° snap applies to the radius line to the slot's middle (Start + Sweep / 2) rather than to the Start Angle; a tap picks an end or the arc centre. Slot's pattern Radius may be 0 (Path Direction only; the generator already handles it): copies turn about the arc centre, so N copies of a 360/N° sweep make a ring. Saved under `body.slot` (sizes in mm), in `TOOL_SHAPES`, the extent and crosshair wiring, `SHAPE_NAMES` / `SHAPE_TABS`, and `HELP_TOPICS`.
- **Checks run:** 7 generator tests (inner / outer paths sampled a bit radius from the slot edge, straight and arc; chord vs radius entry identical; clearing reaches the edge with no gap over a stepover; centre-line direction and G2; origins incl. end centres, arc centre and inset; tabs, patterns, warnings, imperial). Twin comparison extended with five slot cases across all patterns, origins, units and inset (4940 cases, identical). Headless UI: 24 checks in metric and imperial (fields per type and mode, preview, taps, twists, cut-type visibility, tab dots, blocked bad shapes, pattern, Help), plus save / restore in imperial.

### 13. Pattern preview (Rectangle, Circle, Polygon, Slot, Keyhole, Drill)

- **No generator changes.** `updatePatternPreview` runs the current tab's own generator (`PATTERN_PREVIEW_TABS`: form reader + generator name) on its form values with one depth pass (`depth` capped at `depthOfCut`), `tabs: null`, and `clearing` drawn as `inner`, then `traceProgram` reads the G-code back: cutting moves are XY moves below Z0 (G1 lines, G2/G3 with I/J arcs), and a plunge is Z crossing below 0. `drawPatternTrace` fits them into the usual `-50 -50 100 100` view as one SVG path (arcs as SVG arcs, a full circle as two halves), bit-sized dots at the plunges, and `qc-origin-mark` at X0 Y0. Origin, Inset, angle, rotation, extent and honeycomb therefore match Generate without separate drawing code.
- **Size limits:** `computePatternPositions` gives the copy count first. Over `PATTERN_PREVIEW_MAX_OUTLINES` (500) only the plunge dots are drawn (their minimum size shrinks with the count); over `PATTERN_PREVIEW_MAX_COPIES` (3000) nothing is generated and the caption says so. A generator error shows "Fix the shape to preview".
- **Layout:** `mountPatternPreviews` (from `init`) wraps each pattern body's existing children in `.qc-shape-grid` / `.qc-shape-fields` and adds a `.qc-shape-preview-cell` with `svg#qc-<prefix>-pattern-preview`, so the markup is unchanged and the card matches the Shape card (stacks under 600px).
- **Updates:** `schedulePatternPreview` coalesces to one redraw per animation frame. It's called by `input` / `change` listeners on `ROOT` (so they go away with the dialog, per the page-wide-listener rule), `updatePatternVisibility`, `switchTab`, and the six shape-preview functions (twists and origin taps set values without events).
- **Enlarge and drag:** each pattern preview is wired with `wirePreviewAngleDrag` in relative (knob) mode on the pattern Angle, or Start Angle for Circular (an input function, so it follows the style). A tap toggles `.qc-pattern-preview-big` on the cell, which positions it over `.qc-wrapper` (`inset: 16px`), keeps the caption small and shows "Tap or press Esc to return"; the drawing scales with the SVG. `closeEnlargedOnEscape` listens on `window` in the capture phase, so it runs before ncSender's `PluginDialog` Escape listener (bubble phase) and stops the event when it closes an enlarged preview; otherwise Esc closes the dialog as before. It's page-wide, so it removes itself once `ROOT` is detached. `wirePreviewAngleDrag` gained an optional `snap(deg)` argument; the shape previews don't pass it, so their 90° / whole-degree behaviour is unchanged. `snapPatternAngle` rounds to 0.5° and sticks within `PATTERN_ANGLE_SNAP` (1°) of `PATTERN_ANGLE_STOPS`, the multiples of 180/n for n = 3, 4, 5, 6, 8, 10, 12. Caption lines are spaced in `em` so they follow the smaller enlarged font.
- **Checks run:** headless Chrome: simulated drags gave 21.6° -> 22.5, 13.3° -> 13.5, 44.4° -> 45, 26.2° -> 26, and on Circular 35.8° -> Start Angle 36 with the row Angle untouched; a tap enlarged the preview. Earlier: angled Linear rectangles, Circular circles, Path Direction polygons, a radius-0 ring of arc slots, a Honeycomb drill (42 holes) and a 2916-copy start-point grid drew as expected. Node timing on the trace/draw code for 2916 copies: about 12 ms generate, 14 ms trace, 7 ms draw. Installed from a zip in ncSender, the requester confirmed it looks right. Not yet timed on a Raspberry Pi.

## Known limitations / follow-ups

- **Inch-reporting controllers:** with `$13=1` the measure page's distance and coordinates are wrong, though the angle is right. The README documents this.
- **Untested on-screen keyboard:** letters and `"` on the ncSender Pro on-screen keyboard haven't been tested.
- **Tabs are square:** the bit rises straight up over each tab and drops straight back. Ramped (trapezoid) tabs would be gentler on the bit; not done.
